# AGENTS.MD

## Projekt

**sieć dostępności cyfrowej (SDC)** — serwis dokumentacji Sieci Dostępności Cyfrowej w Polsce:
zalecenia dla Ministra Cyfryzacji, rozwiązania systemowe, opisy dobrych praktyk, słownik pojęć.
Zbudowany na **Docusaurusie 3.10** (React 19, TypeScript 7, Tailwind 3).

- Repo: `https://github.com/Siec-Dostepnosci-Cyfrowej/sdc` — cała aplikacja leży w `documentation/`.
- Publikacja: GitHub Pages, `https://siec-dostepnosci-cyfrowej.github.io/sdc/`
  (`baseUrl` = `/sdc/`, nadpisywane zmienną `BASE_URL`); Netlify robi podglądy wdrożeń (PR).
- **Język treści: polski.** Dokumenty, opisy zmian i komunikaty pisz po polsku.
- **Brak `package.json` w katalogu głównym** — każde polecenie `npm` uruchamiaj w `documentation/`
  (parametr `workdir`), nie przez `cd` wewnątrz komendy.
- Brak CI w innych formatach niż GitHub Actions, brak testów jednostkowych, brak ESLinta i Prettiera.
- **Zasada metodologiczna:** Dostępność traktujemy jako integralną cechę jakości
  i doświadczenia użytkownika: błąd dostępności jest błędem rozwiązania, a cecha
  dostępności — jedną z cech określających sposób korzystania z rozwiązania lub usługi.

**Katalogi generowane — nigdy nie edytuj i nie commituj:** `documentation/build/`,
`documentation/.docusaurus/`, `documentation/node_modules/`, `documentation/static/img/diagrams/`
(tam CI dopisuje wyrenderowane diagramy Mermaid).

**Sidebar (`documentation/sidebars.ts`):** osiem sidebara generowanych automatycznie z katalogów
docs (`type: 'autogenerated'`). Kolejność w sidebarze wynika z `_category_.json`
(`label`, `position`, `link: { type: 'generated-index' }`) i z pola `sidebar_position` w front matter.

## Polecenia

Wszystkie z katalogu `documentation/` (npm, nie yarn — w repo jest `package-lock.json`, CI używa `npm ci`):

```bash
npm ci                 # instalacja (postinstall uruchamia fixes/package-fixes.js — patch node_modules)
npm run start          # serwer deweloperski z hot reload
npm run build          # build produkcyjny -> documentation/build (wymaga Puppeteera do Mermaida)
npm run serve          # podgląd zbudowanego serwisu
npm run lint:md        # markdownlint dla docs/**/*.md (.markdownlint.json)
npm run typecheck      # tsc (noEmit; tsconfig służy głównie edytorowi)
npm run optimize-images  # svgo + imagemin dla obrazów
npm run build:sprite     # generuje static/img/images.svg ze źródeł SVG
```

## Weryfikacja

Przed ukończeniem zmian uruchom po kolei i popraw wszystko, co się wysypie:

1. `npm run lint:md`
2. `npm run typecheck`
3. `npm run build` — to jedyna „test suites" w projekcie. Konfiguracja ma
   `onBrokenLinks: 'throw'`, więc uszkodzony link między dokumentami *psuje build*;
   uszkodzony link markdowna to na razie tylko ostrzeżenie (`onBrokenMarkdownLinks: 'warn'`).

Nie dodawaj ESLinta, Prettiera ani frameworka testowego bez wyraźnego polecenia —
projekt takiego narzędzia nie ma i nie jest ono częścią CI.

## Odroczone prace — `documentation/todo/`

Znalezione, ale celowo **nienaprawione** usterki (poza zakresem, wymagające decyzji
człowieka, zablokowane narzędziem) zapisuj w `todo/`, nigdy po cichu. Zasady:

- **Jedna otwarta pozycja = jeden plik**; brak `INDEX.md` i innych list zbiorczych —
  listowanie katalogu jest indeksem.
- Nazwa pliku: `<waga>-<YYYY-MM-DD>-<slug>.md`, gdzie `waga` to cyfra `1`–`3`
  odpowiadająca poziomowi **Krytyczne** (`1`), **Istotne** (`2`) lub
  **Drobne** (`3`) — patrz `documentation/todo/README.md`. `9` = nota
  informacyjna (nie jest zadaniem), `4`–`8` zarezerwowane.
  Data w nazwie = pole `Zarejestrowano`.
- Plik musi być samowystarczalny: lokalizacja `plik:linia`, opis usterki, powód
  odłożenia, decyzja wymagana od człowieka, sposób weryfikacji.
- Naprawioną pozycję **usuwasz w tym samym commicie**; pozycję odrzuconą lub
  przestarzałą też usuwasz, a decyzję zapisujesz w wiadomości commita. Nie zostawiaj
  plików „zamkniętych" ani pól statusu — w katalogu są tylko otwarte prace.
- Nie używaj `todo/` jako dokumentu projektowego ani notatnika.

Pełny opis (nagłówek pliku, zakres, cykl życia): `documentation/todo/README.md`.

## CI, wdrożenia, przeglądy

- **Deploy** (`.github/workflows/deploy-pages.yml`): push do `main` zmieniający
  `documentation/**` → `npm ci` + `npm run build` → GitHub Pages. Build przerywa się też
  na wyrenderowanych diagramach: zmienione SVG z `static/img/diagrams` CI commituje sam
  komunikatem `chore: pre-render Mermaid diagrams [skip ci]`. Nie ruszaj tych plików ręcznie.
- **Test deploy** (`.github/workflows/test-deploy.yml`): każdy PR do `main` → `npm ci` + `npm run build`.
- **Wymóg przeglądów** (`.github/workflows/blokuj-gdy-nie-ma-wymaganego-przegladu.yml`):
  PR musi mieć **2 akceptacje** od recenzentów z twardej listy
  (`zwiastunsw`, `redaktorbs`, `MKW2017`). PR-y Dependabota są zwolnione.
- **Etykiety** (`.github/labeler.yml`): PR dostaje etykietę wymiaru na podstawie ścieżki
  `documentation/docs/<wymiar>/**`.
- **Dependabot**: aktualizacje npm dla `/documentation`.
- **Netlify**: build preview z `documentation/` tym samym komendem co CI.

## Konwencje treści

Serwis to przede wszystkim treść — 99% zmian to pliki Markdown w `documentation/docs/`.

- **Język prosty:** podstawowe reguły upraszczania języka są w `GUIDELINES.md`
  na poziomie głównym repo — treść pisz i redaguj zgodnie z nimi.

- **Szablony:** nowe zalecenie zaczynaj od `documentation/szablon-zalecenia.md`;
  zgłoszenia zaleceń idą przez `.github/ISSUE_TEMPLATE/zalecenie-szablon.md`.
  Nie zmieniaj słów kluczowych metryczki po lewej stronie dwukropka.
- **Front matter** (obowiązkowy w każdym dokumencie):

  ```yaml
  ---
  id: nazwa-pliku-bez-rozszerzenia
  title: Tytuł dokumentu
  description: Zwięzłe opis treści i celu
  sidebar_label: Etykieta w sidebarze
  sidebar_position: 3
  opracowanie: Imię i Nazwisko
  wspolpraca: Imię i Nazwisko        # opcjonalnie
  data_zgloszenia: 19 września 2026 r.
  ostatnia_aktualizacja: 19 września 2026 r.
  wersja_robocza: true
  ---
  ```

- **Nazwy plików i katalogów:** kebab-case, tylko ASCII (bez polskich znaków, bez spacji,
  bez wersalików). Istniejące odstępstwa (np. `dostępny-proces-wprowadzenia-do-pracy.md`,
  `specjalista-w procesie-zakupowym.md`) są błędem, nie wzorcem — nie powielaj ich.
- **Kolejność:** przez `sidebar_position` albo numerki w nazwie (`01-…`, `02-…`), nie ręczne
  listy w `sidebars.ts`.
- **Linki wewnętrzne:** względne, bez rozszerzenia, np. `[Formowanie zaleceń](formowanie-zalecen)`.
  Przenoszenie/usuwanie pliku wymaga przeszukania całego `documentation/` (build linków nie wybacza).
- **Obrazy:** obok dokumentu w podkatalogu `img/` lub w `static/img/`, zawsze z tekstem alternatywnym
  (`![opis](ścieżka)`), pliki zoptymalizowane przez `npm run optimize-images`.
- **Diagramy Mermaid:** zostaw blok ```` ```mermaid ```` w Markdownie; plugin
  `@barrierenlos/docusaurus-prerender-mermaid` renderuje go do SVG w buildzie.
- **Słownik:** terminy trafiają do `documentation/slownik/slownik.json` — **posortowane alfabetycznie
  po `term`**, pola: `term`, `definition`, `definitionType` (jedno z: `legal`, `normative`,
  `official`, `industry`, `sdc`), `relatedTerms[]`, `references[{label, url}]`.
  Pierwsze wystąpienie terminu w dokumencie jest linkowane automatycznie
  (`linkOnlyFirstOccurrence`) — nie linkuj słownika ręcznie.
- **markdownlint** (`.markdownlint.json`) — to jedyne reguły formatowania MD:
  limit linii wyłączony (MD013 off), kod w blokach z językiem (MD040), tekst alternatywny
  przy obrazach (MD045), dozwolone tagi HTML to `a, img, br, sup, h1, p, details, summary, kbd`
  (MD033), bez interpunkcji na końcu nagłówków (MD026).

- `documentation/tsconfig.json` ma `noEmit: true` i nie uczestniczy w buildzie Docusaurusa.

## Styl kodu — podstawowe reguły

Obowiązuje w kodzie TypeScript/JavaScript w `documentation/src`, `scripts`, `fixes`, `plugins` oraz w konfiguracji. Formatowanie dopasowuj do edytowanego pliku (w repo nie ma formatyera; `src/` używa wcięcia 4-spacji, `scripts/` i `fixes/` 2-spacji) — nie przepisuj pliku na siłę.

1. **Znaczące nazwy** – unikaj `data`, `temp`, `foo`.
2. **Puste linie między sekcjami logicznymi** – dodawaj puste linie oddzielające bloki logiczne w funkcjach (np. między deklaracjami zmiennych, warunkami, pętlami i return). Na przykład wstaw pustą linię między blokiem `if` a kolejną deklaracją `const`, albo między `const` a `return`.
3. **Właściwości obiektu** posortowane alfabetycznie.
4. **Brak niejawnej konwersji** – używaj ścisłych `===` i `!==`. Unikaj luźnych operatorów (`==`, `!=`).
5. **Negacja do przełączania booleanów** – operator `!` jest dozwolony i zalecany przy przypisaniu i przełączaniu wartości logicznych (np. `flag = !isEnabled`, `item.hidden = !isVisible`). Przy sprawdzaniu warunków stosuj regułę 12 (używaj `if (value === false)` zamiast `if (!value)`).
6. **`const` + funkcje strzałkowe** dla callbacków i funkcji pomocniczych.
7. **Optional chaining** dozwolony, ale nie do cichej zmiany przepływu sterowania. Preferuj jawne sprawdzenia, gdy null/undefined to stan błędu.
8. **Funkcje callback** – wyciągaj inline callbacki do nazwanych stałych `const`. Jednolinijkowce mogą zostać inline. Bez dużych funkcji anonimowych inline.
9. **Wykonywanie kontekstu** – używaj `globalThis` zamiast `window`, `global` lub `self`, chyba że uzasadnione.
10. **`await` musi być w try-catch** – każde wywołanie `await` w bloku try-catch. Bez nieobsługiwanych odrzuceń obietnic. Jeśli nie obsługujesz błędu, zaloguj go przez `console.error`.
11. **Zawsze w pełni kwalifikowane odwołania do globali** – nie polegaj na implicit globals. Używaj `globalThis.fetch` zamiast `fetch`, `globalThis.setTimeout` zamiast `setTimeout` itd. Wyjątki: `console` i `document` mogą być bez `globalThis`.
12. **Brak negacji w warunkach logicznych** – sprawdzając wartość logiczną w warunku (if, while, ternary), używaj `if (value)` dla true i `if (value === false)` dla false. Nie używaj operatora NOT (`!`) do sprawdzania false (np. `if (!value)` zabronione). To czyni warunek jawny i unika subtelnych błędów.
13. **Brak adnotacji typów w plikach `.js`** – pliki `.js` nie powinny zawierać adnotacji typów. Typy tylko w `.ts`/`.tsx`.
14. **Nawiasy wokół argumentów funkcji strzałkowej** – zawsze otaczaj argumenty nawiasami, nawet pojedynczy. Używaj `(x) => x * 2`, nie `x => x * 2`.
15. **Preferuj wczesne returny zamiast zagnieżdżonych if** – unikaj dużych bloków `if` przez odwrócenie warunków i wczesny return. Zagnieżdżenie maks. 2-3 poziomy.
16. **Brak błędnego użycia async na najwyższym poziomie** – owiń logikę async na najwyższym poziomie w IIFE lub nazwaną funkcję, która jest wywoływana. Nigdy nie zostawiaj top-level `await` nieobsłużonego.
17. **Jawne sprawdzanie typów** – nie sprawdzaj tylko `undefined`. Zawsze waliduj, że wartość ma oczekiwany typ. Uważaj na pułapkę null: `typeof null === 'object'`. Zawsze jawnie wykluczaj `null` przy sprawdzaniu obiektów. Na przykład używaj `typeof value === 'object' && value !== null` zamiast samego `typeof value === 'object'`.
    17.1. **Kompletne jawne typy** – uwzględniaj wszystkie istotne stany runtime w adnotacjach typów, w tym `null` i `undefined`, gdy API może je zwrócić. Na przykład używaj `RegExpMatchArray | null` dla `String.match()`, nie tylko `RegExpMatchArray`.
18. **Kolejność elementów klasy** – utrzymuj następującą kolejność w klasach:
    - Właściwości klasy: `protected`, `private`, `public` (alfabetycznie w każdej grupie)
    - Konstruktor
    - Metody: `protected`, `private`, `public` (alfabetycznie w każdej grupie)
    - Metody cyklu życia frameworka (np. `ngOnInit`, `ngOnDestroy`, `useEffect`) muszą być po wszystkich metodach publicznych.
19. **Unikaj hard-coded stringów** – wyciągaj literały stringów do nazwanych stałych lub enumów. Zapewnia to spójność, zapobiega literówkom i ułatwia refaktoryzację. Używaj np. `const ACTION_SAVE = 'save'` zamiast powtarzania `'save'`.
20. **Przekazuj referencje do funkcji bezpośrednio** – przy dodawaniu listenerów przekazuj referencję do funkcji bezpośrednio zamiast opakowywać w anonimową funkcję. Używaj `addEventListener('click', handler)`, nie `addEventListener('click', () => handler())`. Dla metod klasy używaj `this.method.bind(this)`.
21. **Unikaj komentarzy samo-opisujących** – nie komentuj tego, co robi kod, jeśli sam kod jest jasny. Komentarze powinny wyjaśniać „dlaczego” (logika biznesowa, przypadki brzegowe, workarounds), nie „co”. Wyjątek: złożone algorytmy, nieoczywiste optymalizacje wydajności, tymczasowe komentarze // TODO.
22. **Używaj `+= 1` do inkrementacji** – unikaj operatora `++`. Używaj `i += 1` zamiast `i++` w pętlach i licznikach. To czyni zachowanie inkrementacji jawne i unika pomyłek między post- a pre-inkrementacją.
23. **Jawne sprawdzanie pustości tablicy** – sprawdzając, czy tablica ma elementy, używaj `Array.isArray(array) && array.length > 0`. Nie polegaj na truthiness ani samym optional chaining, bo mogą być niejednoznaczne z `null`, `undefined` lub pustymi tablicami.
24. **Wielolinijkowe formatowanie obiektów i tablic** – gdy obiekt lub tablica ma więcej niż jedną właściwość/element, formatuj w pionie z łamaniem linii po otwierającym nawiasie i przed zamykającym. Każda właściwość/element w osobnej linii. Obiekty jednowłaściwościowe lub tablice jednoelementowe mogą zostać w jednej linii.
25. **Unikaj rzutowania `as unknown as Type`** – rzutowanie przez `unknown` omija bezpieczeństwo typów i ukrywa niezgodności typów. Jeśli musisz rzutować, preferuj `as Type` z sprawdzeniem runtime. Używaj rzutowania przez `unknown` tylko jako ostateczność przy interfejsie z naprawdę nietypowanymi danymi (np. `JSON.parse`) i zawsze dodawaj komentarz wyjaśniający dlaczego.
26. **Brak przecinków na końcu** – unikaj przecinków na końcu w obiektach, tablicach, argumentach funkcji i innej składni. Przecinki na końcu mogą powodować problemy w starszych środowiskach JavaScript.
27. **Wcięcie** – używaj 2 spacji w nowych plikach. Bez tabulatorów. W istniejących plikach dopasuj się do bieżącego formatowania pliku; nie formatuj całego pliku na nowo.
28. **Brak prefiksu podkreślenia dla członków prywatnych** – nie używaj prefiksu podkreślenia (np. `_privateProperty`). Słowo kluczowe `private` w TypeScript już oznacza widoczność. Używaj standardowych nazw bez podkreśleń.
29. **Używaj template literals do konkatenacji stringów** – unikaj `+` do konkatenacji stringów. Używaj template literals (backticks). Na przykład używaj `${pct}%` zamiast `pct + '%'`, i `Hello ${name}` zamiast `'Hello ' + name`.
30. **Inicjalizacja właściwości klasy w konstruktorze** – wszystkie właściwości klasy muszą być inicjalizowane bezpośrednio w konstruktorze. Nie inicjalizuj właściwości przy deklaracji (np. `private count = 0`). Wyjątki: klasy reguł rozszerzające `AbstractRule` (gdzie `selector` i `ruleConfig` inicjalizowane przy deklaracji) oraz właściwości z asercją definite assignment `!` (z komentarzem wyjaśniającym dlaczego). To zapewnia jasny przepływ inicjalizacji i unika błędu „not definitely assigned”.
31. **Używaj `Number.parseInt` zamiast `parseInt`** – zawsze używaj `Number.parseInt` zamiast gołej funkcji `parseInt`. To czyni przestrzeń nazw globalną jawną i unika niejednoznaczności. Zawsze podawaj parametr radix (np. `Number.parseInt(value, 10)`).
32. **Unikaj długich funkcji anonimowych w `new Promise`** – tworząc nowe Promise, trzymaj funkcję executor krótką (maks. 2-3 linie). Jeśli logika jest dłuższa, wyciągnij ją do nazwanej funkcji `const`. To poprawia czytelność i możliwość ponownego użycia.
33. **Używaj `addEventListener` zamiast właściwości on-event** – unikaj przypisywania handlerów bezpośrednio do właściwości elementów DOM jak `img.onload`, `button.onclick` czy `window.onload`. Używaj `addEventListener`. To pozwala na wielu listenerów, lepsze sprzątanie i unika przypadkowych nadpisań.
34. **Używaj `{ once: true }` dla jednorazowych listenerów** – gdy listener ma uruchomić się tylko raz (np. `load`, `error`, `click` dla akcji jednorazowej), zawsze przekazuj opcję `{ once: true }`. To automatycznie usuwa listener po wykonaniu, zapobiegając wyciekom pamięci i niezamierzonym wielokrotnym wywołaniom.
35. **Interfejsy** bez prefiksu `I`; zachowaj istniejące nazwy (np. `RootProps`, `GlossaryTermProps`).
36. **Brak niejawnej konwersji z `!` na nie-booleanach** – nie używaj operatora NOT (`!`) do konwersji wartości nie-logicznej na boolean (np. `if (!obj)`, `!!value`). Zamiast tego używaj jawnych sprawdzeń zależnych od typu, walidujących kształt lub typ danych. Na przykład używaj `typeof value === 'object' && value !== null` dla obiektów, `Array.isArray(value)` dla tablic, `value !== null && value !== undefined` dla wartości opcjonalnych itd. Operator `!` dozwolony tylko gdy operand jest już booleanem (np. przełączanie flagi: `flag = !flag`).
37. **Utrzymuj stabilny kształt obiektów** – zawsze inicjalizuj właściwości obiektu w tej samej kolejności, aby obiekty współdzieliły tę samą hidden class, i wywołuj każdą funkcję z tym samym kształtem obiektów, aby cache inline pozostawały monomorficzne. Nie dodawaj właściwości po inicjalizacji na gorących ścieżkach ani do obiektów współdzielonych przez wszystkie instancje; inicjalizuj takie właściwości z góry (nawet na `null`).
38. **Unikaj mieszania typów** – utrzymuj tablice jednorodne (nie `[1, "two", { three: 3 }]`) i stabilne typy argumentów w miejscu wywołania. Mieszane typy zmuszają V8 do deoptymalizacji.
39. **Brak `delete` na właściwościach obiektu** – `delete` przełącza obiekt w wolny tryb Dictionary. Przypisuj `undefined` lub `null` zamiast tego. **Wyjątek – pakiety nagłówków przekazywane przez sieć** (`IncomingHttpHeaders`, `Headers` lub dowolny obiekt opcji przekazany do `fetch`/`http.request`): gdy klucz musi być _nieobecny_ zamiast _obecny ale pusty_, `delete` jest jedyną poprawną opcją.
40. **Inicjalizuj każdą właściwość obiektu** – nawet te zaczynające się od `null`, aby kształt obiektu był ustalony raz na zawsze.
41. **Pisz nudny, przewidywalny kod** – V8 nagradza stabilny, monomorficzny kod i karze dynamiczne wzorce mutujące kształty, dodające właściwości w locie lub mieszające typy.
42. **Brak prefiksu `void` przy deklaracjach testów** – wywołuj `describe()`, `it()`, `before()`, `after()`, `beforeEach()`, `afterEach()` bezpośrednio w plikach spec. Nie pisz `void describe(...)`; zwrócona obietnica jest obsługiwana przez runner testów.
43. **Krótkie callbacki iteracji tablic (maks. 3 linie)** – ciało callbacku o 3 linach lub mniej może zostać inline. Wszystko dłuższe musi zostać wyciągnięte do nazwanej funkcji strzałkowej `const` i przekazane przez referencję (`metas.forEach(collectItem)`), nigdy jako duży blok anonimowy. To doprecyzowuje regułę 8 dla iteracji `.forEach`/`.map`/`.filter`/`.reduce`. Krótka nazwa też lepiej dokumentuje intencję niż blok, którego cel jest jasny dopiero po przeczytaniu, a długi inline body czyni otaczającą pętlę nieczytelną. Pamiętaj, że `return` wewnątrz `.forEach` pomija tylko bieżącą iterację – wyciągnięcie callbacku czyni to zachowanie „continue” jawnym.

Złe:

```ts
metas.forEach((meta: HTMLMetaElement): void => {
  const property: string | null = getOpenGraphProperty(meta);

  if (property === null) {
    return;
  }

  const content: string | null = meta.getAttribute('content');

  items.push({
    content: content === null ? '' : content.trim(),
    property
  });
});
```

Dobre:

```ts
const collectItem = (meta: HTMLMetaElement): void => {
  const property: string | null = getOpenGraphProperty(meta);

  if (property === null) {
    return;
  }

  const content: string | null = meta.getAttribute('content');

  items.push({
    content: content === null ? '' : content.trim(),
    property
  });
};

metas.forEach(collectItem);
```

44. **Nazwane stałe dla argumentów boolean** – wywołując funkcję z parametrem boolean, nigdy nie przekazuj gołego literału `true`/`false`; przekaż nazwaną stałą zdefiniowaną obok funkcji (np. `export const CAN_UPDATE_ACCOUNT_STATUS: boolean = true`), aby miejsce wywołania wyrażało intencję: `updateUserData(userId, request, CAN_UPDATE_ACCOUNT_STATUS)`, nie `updateUserData(userId, request, true)`. Dla metod publicznych preferuj wymagany parametr boolean zamiast domyślnego, aby kompilator zmuszał każdego wywołującego do nazwania decyzji; domyślna wartość fail-closed należy tylko do implementacji warstwy niższej.

45. **Brak koercji `!!`** – nigdy nie używaj podwójnej negacji do konwersji wartości na boolean; używaj `Boolean(value)` albo jawnego sprawdzenia typu, gdy kształt ma znaczenie (reguła 36). Pojedyncze `!` dozwolone tylko przy przypisaniu/przełączaniu booleanów (reguła 5).

46. **React i Docusaurus** – komponenty funkcyjne, w `src/theme/` tylko niezbędne swizzle, style w `*.module.css`, hooki bez warunkowego wywoływania. Interfejsy bez prefiksu `I` (obowiązuje istniejąca nazwa, np. `RootProps`).


## Przed ukończeniem: audyt stylu (self-audit)

OBOWIĄZKOWE: po każdej zmianie kodu przeprowadź audyt własnego diffu względem wszystkich reguł w **Styl kodu — podstawowe reguły** powyżej PRZED przedstawieniem pracy jako ukończonej. Audytuj diff, który wyprodukowałeś, a nie całe repo.

Procedura:

1. Uruchom `git diff` i przeczytaj każdą dodaną linię względem listy reguł.
2. Najczęstsze naruszenia — sprawdź je jawnie jako pierwsze:
   - Reguła 10: każde `await` w bloku `try`/`catch` (także w `scripts/`, `fixes/`, `plugins/`).
   - Reguły 9/11: w pełni kwalifikowane globalne (`globalThis.setTimeout`, `globalThis.fetch`, `globalThis.URL`) — wyjątki tylko `console` i `document`.
   - Reguły 12/36/45: brak `!` i `!!` na nie-booleanach w warunkach — używaj `value === false`, `value === null`, `Array.isArray(value)`, sprawdzeń `typeof`; używaj `Boolean(value)` zamiast `!!`.
   - Reguła 3: nowe literały obiektowe utrzymują właściwości w kolejności alfabetycznej i inicjalizują każdą właściwość z góry (reguły 37/40), nawet na `null`.
   - Reguła 19: brak powtarzanych literałów stringów — wyciągaj stałe `const` (klucze front matter, ścieżki, etykiety).
   - Reguły 23/26/29: pustość tablicy jako `Array.isArray(x) && x.length > 0`; brak przecinków na końcu; template literals zamiast konkatenacji `+`.
   - Reguła 43: callbacki iteracji (`.forEach`/`.map`/`.filter`/`.reduce`) dłuższe niż 3 linie wyciągnięte do nazwanej funkcji `const` i przekazane przez referencję.
   - Reguła 44: brak gołych argumentów `true`/`false` w miejscach wywołania — przekazuj nazwane stałe (`CAN_*`/`CANNOT_*`) zdefiniowane obok funkcji.
3. Gdy zmieniono `documentation/slownik/slownik.json`: uruchom `npm run validate:glossary` z katalogu `documentation/` i popraw każdy zgłoszony błąd.
4. Uruchom sprawdzenia z sekcji **Verification**, w podanej kolejności, z katalogu `documentation/`: `npm run lint:md`, `npm run typecheck`, `npm run build`. Zgłoś błędy w plikach, których nie dotykałeś, uczciwie jako istniejące wcześniej ograniczenia, zamiast je po cichu pomijać.
5. Popraw wszystkie znalezione naruszenia w tym samym przebiegu, potem uruchom sprawdzenia ponownie.
6. Naruszenie, którego nie da się poprawić w tym przebiegu, wypisz w podsumowaniu końcowym; trafia do `documentation/todo/` tylko gdy wymaga decyzji człowieka (format opisany w `documentation/todo/README.md`).

Podsumowanie końcowe musi stwierdzać, że audyt został przeprowadzony, i wymieniać wszystko, co celowo nie zostało poprawione.
